## Причины и степень уверенности

**Подтверждено: задержка доставки на сервере преимущественно возникает до socket write.**
Enqueue будит до 1202 persistent writer-горутин на один тик. Сами записи короткие, а очередь ожидания исполнения даёт p99 ~29 ms. Выбор получателей и world step существенно дешевле.
Это согласуется с конкуренцией горутин за выполнение при массовом пробуждении. Без CPU/trace под нагрузкой нельзя разделить стоимость runtime scheduling, конкуренцию за общие метрики/atomics и планирование WSL/Windows.

Go scheduler histogram показывает ~10% наблюдений в широком bucket **10.49–117.44 ms**. Его интерполированный p99 ~107 ms нельзя трактовать как измеренную точную задержку 107 ms: bucket слишком широкий. Даже средние runtime histogram могут быть приближёнными. Для точного разделения нужен runtime trace.

**Сильная гипотеза: скачки wall clock WSL искажают возраст кадра и влияют на TiDi.**
В 08:58:10 лог фиксирует `write_pressure_ms=2006`, compute=57 ms, fanout=5 ms и переход 100→90%.
В scrape 08:58:13.062 одновременно добавились:

- 494 наблюдения возраста кадра **до** socket write >1 s;
- 496 наблюдений возраста кадра **после** socket write >1 s;
- лишь 1 наблюдение ожидания **после enqueue** >1 s;
- ни одного socket write >250 ms за всё выгруженное окно.

При этом промежуток между scrape 08:58:06.099 и 08:58:13.062 равен 6.963 s, а счётчик тиков вырос всего на 96 — примерно на 5 s работы при 20 Hz. Похожие сдвиги есть даже до нагрузки и после неё. Например, 08:57:34.154→08:57:41.099: 6.945 s и ровно 100 тиков.

Код в `broadcast.go` считает queue/state age вычитанием `time.Now().UnixNano()`, но tick/fanout/write duration — через `time.Since()`. Разница clock domains объясняет одновременный большой state age и короткие измеренные операции. На хосте подтверждён WSL2. Это не доказывает конкретную службу синхронизации или отличает её от особенностей паузы VM; исторических host/clock traces нет.

Первое исправление для следующего изменения: измерять все внутрипроцессные интервалы монотонными часами; удобно хранить int64 от общего process epoch через `time.Since(epoch).Nanoseconds()`, сохранив размер writeJob. Unix timestamps оставить для логов. Отдельно проверить staleness/activity расчёты — они также используют UnixNano. [Go рекомендует монотонное время для измерения интервалов](https://pkg.go.dev/time#hdr-Monotonic_Clocks).

**Подтверждён риск регулятора: максимум одного writer управляет скоростью всего мира.**
Каждый writer обновляет общий `writePressurePeakNs`; fanout забирает максимум через atomic swap и передаёт его в `tuneTimeDilation`. Таким образом, единичный медленный клиент или ложный clock spike влияет на всех.
В рабочем дереве уже есть debounce и floor 30%; они уменьшают чувствительность, но не устраняют зависимость от максимума. Точное соответствие бинарника незакоммиченным изменениям не установлено: image ID и start time сохранены, build revision endpoint отсутствует.

Следующее улучшение регулятора после исправления часов: принимать глобальное решение по устойчивой доле опоздавших получателей/нескольким тикам, а медленные отдельные соединения ограничивать индивидуально. Проверять также фактическое движение и свежесть кадров: уменьшение числа рассылок само по себе улучшает серверный p99 ценой задержки игроков.

На плато gauges показывают 100%/50 ms при каждом scrape, но логи между scrape фиксируют краткие 100→95%. Интервал сбора 5 s скрывает быстрые переходы. `997 / 53.871 ≈ 18.51 Hz` — rate по настенному времени; из-за clock anomaly это нельзя объявлять доказательством пропуска ~7.5% simulation ticks.

## Ограничения нагрузочного сценария и клиента

Локальный Artillery YAML действительно создаёт 1200 arrivals: две фазы по 60 s × 10/s. Цикл каждого бота содержит think **0.5 + 2 + 5 + 0.5 = 8 s**, count=25. Основной MOVE вызывается примерно раз в 8 s, а не 2 раза в секунду, как утверждает комментарий. Это объясняет короткое плато и растянутый уход клиентов.

Процессор шлёт бинарные пакеты через `context.ws.send`. Старые beforeRequest/afterResponse hooks парсят JSON и не привязаны в сценарии к этим send; matching nonce/ACK отсутствует. `game.message.latency_ms` не является достоверным игровым RTT. Боты не валидируют server state и не повторяют browser gap→SYNC_REQUEST поведение. Массовый resync от настоящих клиентов этим тестом не проверен.

При следующем тесте добавить настоящий application PING/PONG с nonce и монотонным временем, MOVE→ACK по sequence, frame arrival interval/gaps и event-loop lag генератора. Профиль движения брать из актуального клиента: нельзя просто менять rate по устаревшему RAG. MOVE формата 6 bytes соответствует текущему decoder; RAG описывает старую версию протокола 4, а код уже имеет ProtocolVersion=6.

В браузере remote interpolation явно добавляет **50–150 ms**, стартовое значение 75 ms (`playerManager.ts`). При базовых 20 Hz ввод также ожидает ближайший simulation tick. Поэтому p99 write completion 34 ms не означает, что движение других игроков видно через 34 ms. Уменьшение interpolation buffer следует проверять по реальным arrival gaps, иначе появляются заметные остановки/рывки. Artillery не измеряет этот визуальный этап.

## Порядок дальнейшей оптимизации

1. Устранить зависимость измеряемых интервалов и pressure control от wall clock. Добавить tick-start lateness, счётчик изменений TiDi и долю кадров старше порога; сейчас короткие провалы скрываются за scrape.
2. Повторить одинаковый 1200-client тест с измерением RTT/ACK и event-loop lag, сохраняя CPU profile и короткий runtime trace **на плато**. Нужны метрики хоста и контейнеров: сейчас в Prometheus есть только game target, нет node-exporter/cAdvisor. Artillery report за завершённый запуск локально не найден, место запуска генератора не установлено.
3. Сравнить такой же тест на Linux-хосте и с генератором на отдельной машине. Запуск на Windows при сервере в WSL разделяет процессы, но они продолжают конкурировать за физический CPU и RAM.
4. По профилю сравнить ограниченную конкурентность socket writers и текущую модель 1200 одновременных пробуждений. Это эксперимент с ограничением freshness, а не гарантированное ускорение: слишком маленький pool создаст head-of-line blocking. Сравнивать queue/state age/RTT, не только fanout enqueue.
5. После стабилизации доставки уменьшать interpolation buffer и оценивать 20→30/40 Hz. Рост tick rate увеличит число пробуждений и writes; включать его до решения очередей рискованно для хвостов.

Byte budget/AOI в этом прогоне не доказаны первоочередным решением. Velocity replication уже включена; payload в среднем ~1.1 KB. Ограничение получателей может провоцировать sequence gaps и дополнительные full sync у настоящего браузера. GC tuning также не поддерживается данными как главный приоритет.

Работающий сервер не перезапускался, исходный код и конфигурация не менялись. Сохранены доказательства и воспроизводимый анализ; ускорение после исправлений этим исследованием ещё не измерено.
